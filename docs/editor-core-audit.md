# 编辑器核心功能与 UI 可用性审计

生成日期：2026-06-04

## 1. 审计结论摘要

本次审计围绕 `ROADMAP.md` 中的 MVP 黄金路径执行：

`数据接入 -> 字段识别 -> 图表配置 -> 画布排版 -> 保存恢复 -> 导出运行`

总体判断：当前编辑器已经具备可演示的原型能力，任务加载、探针取数、添加图表、拖拽、保存、刷新恢复、预览、导出代码都能跑到对应入口。但它还没有形成可靠 MVP，最大阻断点是数据契约和字段识别不稳定，导致 mock 数据进入图表后只能得到数字 key，图表显示为 `[object Object]` 和接近 0 的数值。保存和导出会把这个错误绑定继续固化。

优先级判断：

1. 先统一 `globalData` 数据契约和字段推导。
2. 再修图表绑定、运行时渲染和导出代码的一致性。
3. 然后补编辑器 UI 基线和可用性。
4. 模板系统目前还没有真实实现，不建议现在先做复杂模板库。

## 4. 关键阻断问题

### P0-1：前后端 Schema 契约不一致

当前前端 store 的 `DashboardSchema` 使用：

- `components`
- `globalData`
- `canvas`

但后端 `taskController.ts` 的类型和默认 schema 仍使用：

- `components`
- `assets`
- `canvas`

真实 `tasks.json` 里也同时存在两种形态：旧任务包含 `globalData`，新建任务包含 `assets: []`。这会让新任务加载后 `globalData` 为空，也会让保存前后的 schema 形态发生变化。

建议：第一优先级统一后端类型、默认 schema 和现有数据文件，全部以 `globalData` 为准。

### P0-2：字段识别只读顶层 key，无法消费数组对象

ROADMAP 已指出这个问题，本次浏览器实测再次确认。远程 mock 返回数组：

```json
[
  { "month": "1月", "sales": 150, "profit": 80, "target": 200 }
]
```

但默认过滤器 `return { ...res }` 会把数组变成：

```json
{
  "0": { "month": "1月", "sales": 150 }
}
```

最终可用字段只有 `0,1,2,3,4,5`。添加图表后 X 轴显示 `[object Object]`，Y 轴被 `Number(object)` 转成 0。

建议：定义标准数据形态，例如：

```json
{
  "month": ["1月", "2月"],
  "sales": [150, 230]
}
```

并把 `dataHelper.ts` 的数组字段提取能力接入探针或 store。

### P0-3：运行时渲染和导出逻辑不同构

运行时 `ComponentWrapper.tsx` 支持：

- `title`
- `color`
- `useCustomDataCode`
- `customDataCode`
- `customOption`

但 `codeGenerator.ts` 主要使用：

- `chartType`
- `xAxisField`
- `yAxisField`
- `customOption`

导出代码没有完整复用运行时逻辑，尤其没有处理 `title/color/useCustomDataCode/customDataCode`。这会导致编辑器中能显示的配置，导出后不一定一致。

建议：优先让导出逻辑与运行时图表 option 生成逻辑共享同一套数据理解。

## 6. UI 可用性问题

| 等级 | 问题 | 影响 |
| --- | --- | --- |
| 阻断操作 | 组件靠近右侧配置面板时，右侧缩放手柄可能被面板遮挡或难以操作。 | 缩放体验不稳定，尤其是大画布和右侧面板同时存在时。 |
| 明显影响效率 | 左侧、画布、右侧都有独立滚动条，页面还有外层滚动条。 | 容易迷失滚动位置，拖拽和配置时割裂。 |
| 明显影响效率 | 全局数据预览使用只读 textarea，数据稍大时阅读体验差。 | 不利于判断字段结构，也不利于发现数组对象形态。 |
| 明显影响效率 | 右侧配置面板很长，需要频繁滚动；危险操作区占据首屏。 | 常用字段绑定和标题配置被挤压，操作成本高。 |
| 明显影响效率 | 预览模式没有真正隐藏顶部工具栏和滚动条。 | 与“全屏预览”的用户预期不一致。 |
| 纯视觉优化 | 编辑器仍有大量内联样式、emoji 文案和旧式 Element Plus 默认视觉。 | 和任务大厅新 UI 基线不统一。 |
| 纯视觉优化 | 空状态、面板标题、按钮图标和文案层级不够专业。 | 会影响产品可信度，但低于功能闭环问题。 |

## 7. 推荐下一步实现顺序

1. **统一 Schema 契约**
   - 后端默认 schema 改为 `globalData: null`。
   - 移除或兼容迁移 `assets`。
   - 保证新建、保存、复制任务都产出同一种 schema。

2. **接入统一字段推导**
   - 明确 `globalData` 标准形态。
   - 让 mock 数组能自动变成字段数组。
   - 将 `dataHelper.ts` 接入探针执行结果或 store 写入入口。

3. **修图表绑定和渲染**
   - 让字段下拉出现 `month/sales/profit/target`。
   - 添加柱状图后默认绑定一个维度字段和一个数值字段。
   - 图表显示真实月度销售数据，而不是 `[object Object]`。

4. **对齐导出代码**
   - 复用运行时 option 生成规则。
   - 支持 `title/color/customDataCode/customOption`。
   - 导出结果必须和编辑器画布一致。

5. **保存恢复回归**
   - 用一份标准 mock 数据创建图表。
   - 拖拽、缩放、保存、刷新后确认完全一致。
   - 再验证导出代码包含同样的数据和图表配置。

6. **编辑器 UI 基线优化**
   - 在功能闭环稳定后，参考 `editor-light-workbench.png` 和 `editor-clean-light.png`。
   - 重点改面板结构、滚动、配置层级、全屏预览和 JSON/JS 编辑器。

7. **模板系统后置**
   - 当前模板入口只是占位。
   - 等数据契约、保存恢复、导出稳定后，再设计“从模板创建任务”和“编辑器加载模板”的流程。

## 9. 审计后修复进展

更新日期：2026-06-05

本节记录审计后已经完成的一版修复，保留前文审计结论作为历史问题来源。

### 已完成

- 后端新建任务默认 schema 已改为 `globalData: null`，不再生成 `assets: []`。
- `DashboardSchema.globalData` 已统一为字段数组对象或 `null`。
- 探针默认 JS 已改为极简用户自定义入口，不再内置大段自动转换逻辑。
- 探针支持多次导入数据源，已有全局数据后入口文案为“导入更多数据源”。
- JS 过滤结果写入前会校验：必须返回普通对象，且每个字段值必须是数组。
- 同名字段导入前会显示覆盖字段，并在真正写入前二次确认。
- `mergeGlobalData` 已改为字段级合并：新字段追加，同名字段整列替换。
- 图表字段识别已从 `globalData` 顶层数组字段推导，添加图表时会优先选择维度字段和数值字段。
- 图表运行时会对缺字段、空数组、长度不一致、Y 轴非数值等情况显示提示。
- 导出代码已按同一套字段数组理解生成图表 option，并包含 `title`、`color`、`customOption`。
- 全量编辑全局数据弹窗已放大、支持拖动和调整大小，并新增 JS 筛选模式。

### 已验证

- 前端：`npm.cmd run build` 通过。
- 后端：`npm.cmd run typecheck` 通过。
- 浏览器验证过首次导入、二次导入、同名字段覆盖提示、覆盖确认、预览结果导入。
- 浏览器验证过全量编辑弹窗放大、可拖动、可调整大小和 JS 筛选入口。

### 仍待后续处理

- v1 只保存最终 `globalData`，不保存每次数据源 URL、请求参数和 JS 脚本历史。
- 探针 JS 仍是用户代码执行能力，后续需要补安全边界和生产化限制。
- 模板系统仍未实现。
- 普通表格、指标卡、文本等常用大屏组件仍未加入。
- 编辑器 UI 基线、组件操作体验和自动化测试仍需继续推进。
